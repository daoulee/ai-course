## 2~3. 프롬프트 측정과 수정 (`evalprompt.py`, `p1.txt`~`p4.txt`)

같은 프롬프트를 5번 돌려서 테스트 10개 통과 수의 평균을 냈다.

| 파일 | 추가한 것 | 평균 | 회차별 |
| --- | --- | --- | --- |
| `p1.txt` | 한 줄 요청 | **0.0** | 0, 0, 0, 0, 0 |
| `p2.txt` | 함수 이름, 결과 형식, 코드만 출력 | **4.2** | 4, 4, 4, 5, 4 |
| `p3.txt` | 규칙 목록 | **9.0** | 9, 9, 9, 9, 9 |
| `p4.txt` | 010은 11자리만 | **9.6** | 9, 10, 10, 10, 9 |

**p1**은 5번 모두 `normalize_phone 없음`이었다. 함수 이름을 안 정해 줬으니 테스트가 함수를 찾지 못한다.

**p2**에서 실패한 입력은 매번 거의 같았다.

```
'+82 10-1234-5678' -> '+82 10-1234-5678'
'02-123-4567'      -> '02-123-4567'
'010-abcd-5678'    -> '010-abcd-5678'
''                 -> ''
'011-123-4567'     -> '011-1234-567'
```

+82, 지역 번호, 글자 섞인 입력, 빈 문자열에 대해 프롬프트가 아무 말도 안 했으니 모델은 입력을 그대로 돌려줬다.
실패 목록이 곧 프롬프트에 빠진 규칙 목록이다.

**p3**는 5번 모두 9/10이고, 틀린 건 다섯 번 다 `'010-1234-567' -> '010-123-4567'` 하나였다.
숫자만 세면 01로 시작하는 10자리라 규칙 넷째 줄대로면 이게 맞는 답이다. 모델이 틀린 게 아니라 규칙과 테스트가 서로 어긋나 있었다.
010은 11자리뿐이라는 사실이 규칙에 없었다.

**p4**에서 그 줄을 고치니 10/10이 세 번 나왔다. 나머지 두 번은 여전히 같은 입력에서 틀렸는데,
규칙에 적어도 temperature 0.7에서는 가끔 흔한 방식(10자리면 3-3-4)으로 돌아간다.

실습 서버에서 요청 하나가 8분 넘게 응답이 없어서 측정이 멈춘 적이 있었다.
`OpenAI(..., timeout=120)`을 넣어서 한 요청이 오래 걸리면 오류로 끝나게 했다.

## 4. 모델에게 질문받아 스펙 정하기 (`todo/SPEC.md`)

"코드는 쓰지 말고 질문해 줘"라고 보내니 gemma4가 질문 다섯 개를 했는데, 권하는 답이 이랬다.

| 질문 | 모델이 권한 답 | 내가 정한 것 |
| --- | --- | --- |
| 로그인이 필요한가 | 예 (회원가입/로그인 포함) | 없음 |
| 할 일에 저장할 정보 | 제목, 내용, 완료 여부, 생성 날짜, 마감 기한 | 제목, 완료 여부, 만든 시각 |
| 우선순위나 태그 | 예 | 없음 |
| 디자인 | Bootstrap 같은 프레임워크 | HTML과 CSS만 |

권하는 답은 전부 "흔한 할 일 앱"이었다. 정하지 않고 넘어갔으면 이게 그대로 스펙이 됐을 것이다.
빈 제목, 100자 초과, 없는 번호 처리는 모델이 묻지 않아서 내가 먼저 적어 줬다.

모델이 쓴 SPEC.md 초안을 강의서의 세 가지 기준으로 고쳤다.

| 확인 | 찾은 것 | 고친 것 |
| --- | --- | --- |
| 정한 것이 다 들어갔나 | 들어감 | - |
| 정하지 않은 게 들어갔나 | `static/css/style.css` 경로, `database.db` 이름 | 경로를 정리 |
| 6절이 4절을 다 검사하나 | 3절 파일 구성에 `test_app.py`가 없음. 100자 경계값 테스트가 없음 | 추가 |

## 6. 버그 수정 요청 두 가지 (`bugs/`)

처음 `test_grades.py`는 2/8 통과였다. 같은 gemma4에 두 가지 요청을 보냈다.

| | 한 줄 요청 | 재현 방법, 실제 결과, 범위를 준 요청 |
| --- | --- | --- |
| 테스트 | 8/8 | 8/8 |
| 바뀐 줄 | +13 / -6 | +10 / -6 |
| 테스트와 관계없는 변경 | 주석 4줄 추가 (`# 경계값 포함을 위해 >= 권장` 등) | 없음 |
| 고친 이유 설명 | 코드 아래 일반 설명 | 고친 줄마다 원인 한 줄씩 |

이번엔 둘 다 통과했다. 버그가 다섯 개뿐인 짧은 파일이라 한 줄 요청으로도 찾을 수 있었다.
차이는 바뀐 범위였다. 범위를 안 정하면 요청하지 않은 주석까지 덧붙인다. 파일이 크면 이게 함수 이름이나 구조 변경이 된다.

둘 다 `pass_rate`가 `75.0`(실수)을 돌려주는데 테스트는 `75`와 비교해서 통과한다. 파이썬에서 `75.0 == 75`가 참이라서다.

## 7. 코드 검토 (직접 해보기 8)

세 가지 관점(SQL에 입력을 직접 넣는가, 길이 검사가 빠졌는가, 없는 번호에 500이 나는가)으로 검토를 시켰더니 셋 다 "해당 없음"이었다.
직접 확인해 보니 맞았다.

- SQL 다섯 곳 모두 `?` 자리 표시자를 쓴다. `'); DROP TABLE todos;--`를 제목으로 넣어도 그냥 글자로 저장된다
- `/toggle/abc`, `/delete/-1`은 `<int:>` 변환기에서 걸러져 404
- `title` 필드가 아예 없어도 `.get("title", "")`이라 400

4주차에서 모델이 없는 걸 있다고 답한 적이 있어서 의심했는데, 이번엔 없는 문제를 지어내지 않았다.

## 정리

- 프롬프트에 안 적은 부분은 모델이 정한다. 같은 요청도 매번 다르게 정한다.
- 프롬프트가 좋아졌는지는 한 번 읽어 봐서는 모른다. 여러 번 돌려 테스트 통과 수로 비교해야 한다.
- 실패한 입력을 읽으면 프롬프트에 빠진 규칙이 보인다.
- 실패가 모델 탓이 아니라 규칙과 테스트의 모순일 때도 있다. 테스트가 있어야 그걸 찾는다.
- 스펙은 모델에게 질문받아 정하되, 모델이 권하는 답은 "흔한 것"이라 내 범위와 다르면 직접 정해야 한다.
- 작업은 명령 하나로 확인되는 단계로 나누고 단계마다 커밋한다.
- 버그 수정은 재현 방법, 실제 결과 원문, 범위를 같이 준다. 범위가 없으면 요청 안 한 곳까지 바뀐다.
- 검토 결과는 직접 재현해서 확인한다. 리팩터링은 테스트를 안 고치고 전부 통과하는지로 확인한다.
- 반복되는 지시는 `.clinerules`, 어디까지 했는지는 `PROGRESS.md`에 둔다.
