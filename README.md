### 5절. 컨텍스트가 길어지면 VRAM을 더 쓴다

| num_ctx | `ollama ps` SIZE | `ioreg` 실측 |
| --- | --- | --- |
| 2,048 | 5.6GB | 6.71GB |
| 4,096 | 5.9GB | 6.98GB |
| 8,192 | 6.6GB | 7.66GB |
| 16,384 | 7.9GB | 8.75GB |
| 32,768 | 10GB | 11.05GB |

4096에서 5.9GB, 8192에서 6.6GB로 강의서 값과 정확히 일치했다.
측정값으로 KV 캐시를 역산하면 `(10 − 5.9)GB ÷ (32,768 − 4,096)토큰 = 150KB/토큰`으로,
강의서의 이론값 147KB(36층 × 2 × 1024차원 × 2바이트)와 거의 같다.

옵션 없이 호출하면 CONTEXT가 강의서의 4096이 아니라 **32768**로 잡힌다.
Ollama 0.33이 가용 메모리에 맞춰 컨텍스트를 자동으로 키우기 때문이다.
8GB 장비였다면 4096으로 줄었을 것이므로, 4096은 고정값이 아니라 장비에 따른 값이다.

### 직접 해보기 9. 모델 크기와 속도 (`speed.py`)

| 모델 | PROCESSOR | 측정 속도 | 강의서 상한 (RTX 4060) | 상한 대비 |
| --- | --- | --- | --- | --- |
| qwen3:1.7b | 100% GPU | 초당 199.8토큰 | 194 | 103% |
| qwen3:8b | 100% GPU | 초당 63.6토큰 | 52 | 122% |

둘 다 강의서의 상한을 넘었다. 상한은 RTX 4060의 VRAM 대역폭 272GB/s로 계산한 값인데,
M4 Max의 통합 메모리 대역폭이 그보다 높아서 상한 자체가 다르기 때문이다.
속도가 모델 크기에 반비례한다는 관계(1.7b가 8b보다 3.1배 빠름)는 그대로 성립한다.

**모델 크기의 벽은 이 장비에서 재현되지 않았다.** 27GB 상한에 8b(5.2GB)도 14b(9.3GB)도
여유롭게 들어가서 PROCESSOR가 계속 `100% GPU`다. 벽을 보려면 GPU 상한을 인위적으로 낮춰야 한다.

```
sudo sysctl iogpu.wired_limit_mb=6144   # GPU 상한을 6GB로 낮춘다
sudo sysctl iogpu.wired_limit_mb=0      # 원복 (재부팅해도 원복된다)
```

### 도전. 1주차 실험을 내 GPU에서 (`matmul.py`)

맥에는 cuda가 없어서 `torch.cuda`를 Metal용 `torch.mps`로 바꿨다.
mps는 첫 연산에 셰이더를 컴파일하므로 워밍업 없이 재면 GPU가 CPU보다 느리게 나온다.
워밍업 한 번 + 5회 평균으로 측정했다.

| 장비 | CPU | GPU | 배수 |
| --- | --- | --- | --- |
| Colab T4 (1주차) | 1.0334초 | 0.0457초 | 23배 |
| M4 Max (4주차) | 0.0610초 | 0.0130초 | 4.7배 |

배수는 T4보다 작지만 CPU 시간 자체가 17배 빠르다. T4의 배수가 큰 것은 GPU가 빨라서가 아니라
Colab의 CPU가 느렸기 때문이다. 배수만 보면 장비의 성능을 잘못 읽게 된다.
